strategies — when and how faults fire
Manual / On-demand
runner.start() · runner.stop()
inject() context manager
Developer controls timing explicitly.
Percentage-Based
Latency(2.0, probability=0.30)
Fires on random X% of requests.
Roll made once per request.
Cycling — door()
Alternates fault-ON / fault-OFF
for N cycles. Measures recovery
between each cycle.
Ramp-Up / Progressive
Increase fault intensity over time.
Finds the breaking point.
(R10 — Progressive Overload)
Timed Auto-Stop
runner.start(duration="10m")
Background timer stops fault
automatically after duration.

target plane — where faults land
LoggingTarget  transparent proxy

Faults always call LoggingTarget — never the real target directly.
Intercepts every run() and sudo() → writes to SessionDB.

injection mechanisms — how faults reach the system
Depth 1 — OS / Kernel
Runs privileged commands on the target machine.
tc netem stress-ng pkill systemctl docker dd
Requires: Linux + sudo
Depth 2 — HTTP Proxy
MITM proxy sits between SDK and real API.
Point SDK at localhost:<port>
LLMLatency LLMRateLimit LLMHallucination SemanticCorrupt
Depth 3 — Transport Patch
Monkey-patches httpx.Client.send
Works on any OS — no sudo, no port, no proxy.
inject() Latency RateLimit Timeout Unavailable
